# 03 · L2 入库管线与用户确认页

> **日期**：2026-07-15
> **解决根因**：3（隐含前提）、4（视觉像素）、5（物理版面）、9（极性，离线侧）
> **核心设计**：结构解析（正则为主）→ 用户确认 → LLM 批量抽取（省调用）→ 双写

---

## 1. 入库流程总览

```
用户上传 PDF
      │
      ▼
 ① MinerU 解析（已有）→ Markdown + 图片
      │
      ▼
 ② GbDocumentStructureParser（正则为主，LLM fallback）
    → 识别标准号/版本/章条款层级树
    → 标记条款解析质量评分（🟢高/🟡中/🔴低）
    → 特殊处理：范围条款、规范性引用文件、术语定义、附录
      │
      ▼
 ③ 【用户确认页】（PARSED 状态）
    → 左侧：PDF 原文（PDF.js 渲染，支持翻页）
    → 右侧：解析结果（章节树 + 条款详情 + 质量标记）
    → 交互：点击条款 → PDF 自动跳转对应页
    → 操作：确认 / 编辑 / 重新解析 / 取消
      │
   确认 │
      ▼
 ④ GbSchemaDeriver（每标准 1 次 LLM）
    → 输入：前言 + 目录 + 前3章
    → 输出：domain_schema（4 槽位的 label/enum/unit）
      │
      ▼
 ⑤ LLM 批量抽取（1 次 batch，N 个条款打包）
    → 单次调用同时产出：
        a) 每条款 4 槽位值（符合 domain_schema）
        b) 每条款极性（positive/negative/exception）
        c) gb_parameter 参数提取
        d) gb_reference 引用关系提取
    → 配合正则预筛：条款号、标准号引用先用正则抽，LLM 只补复杂语义
      │
      ▼
 ⑥ 双写：
    a) 结构化表：gb_standard + gb_clause + gb_parameter + gb_reference + gb_term_dict
    b) 向量库：airag_embedding（metadata 注入 4 槽位 + clause_path + standard_no + polarity）
      │
      ▼
 ⑦ 审计埋点：每条款入库记录写 gb_audit_log（P2 起强制）
```

## 2. 为什么 LLM 抽取在用户确认之后（关键设计）

旧设计（根因文档 legacy）把 LLM 抽取放在用户确认之前——等于在**可能错误的结构**上白跑几百次 LLM。

新设计：MinerU 解析质量不可控（见 legacy 实测：GB 38031 条款号丢失小数点"31"应为"3.1"）。**先让用户确认结构对了**，再跑 LLM。这样：
- 省钱：错误结构不会触发 LLM 调用。
- 省时：用户驳回重解析，不会浪费已跑的 LLM 配额。
- 质量高：LLM 在正确结构上抽，准确率更高。

## 3. GbDocumentStructureParser — 结构树解析（正则为主）

### 3.1 解析策略（优先级从高到低）

1. **正则匹配国标编号规范**：`^(\d+)(\.\d+)*\s+(.+)$`（国标条款号有规范格式，正则比 LLM 准、便宜 1000 倍）
2. **Markdown 标题层级**：`#` / `##` / `###`
3. **OCR 退化修复**：检测 "31" 可能是 "3.1"（根据上下文推断，如前后都是"3.x"序列）
4. **LLM 辅助补全**：正则和标题都无法确定时才调 LLM（fallback，非主路径）

### 3.2 特殊处理

| 章节 | 处理 | 落地 |
|------|------|------|
| 第1章 范围 | 标记 `is_scope=true` | gb_clause |
| 第2章 规范性引用文件 | 提取标准号列表 | gb_standard.normative_refs |
| 第3章 术语和定义 | 提取术语 | gb_term_dict |
| 附录 A/B/C | 标记 `is_appendix=true`，字母编号 | gb_clause.appendix_label |
| 注（Notes） | 关联所属条款 | gb_clause.metadata |
| 表格 | 保持与所属条款关联 | gb_clause.text 内联 |

### 3.3 解析质量评分

每个条款标记质量分（🟢高/🟡中/🔴低），依据：
- 条款号是否匹配正则
- 标题是否存在
- 文本是否完整（无截断）

用户确认页据此高亮低质量条款，提示重点校对。

## 4. 用户确认页

### 4.2 前端组件

|------|------|------|

## 5. GbSchemaDeriver — domain_schema 推导（每标准 1 次 LLM）

### 5.1 输入输出

- 输入：标准的前言 + 目录 + 前3章内容
- 输出：该标准的 `domain_schema` JSON（4 槽位的 label/enum/unit）

### 5.2 LLM Structured Output

```json
// GB 31241 推导结果
{
  "primary_type":   {"label":"测试类型", "enum":["overcharge","short_circuit","crush","thermal_shock","drop","nail_penetration"]},
  "secondary_type": {"label":"对象类型", "enum":["cell","pack","system"]},
  "quantity_value": {"label":"电池串数", "unit":"S"},
  "condition_text": {"label":"环境温度", "unit":"℃"}
}

// GB/T 34131 推导结果（完全不同的领域，但 4 槽位列名不变）
{
  "primary_type":   {"label":"功能类别", "enum":["BMS功能","热管理","电气安全"]},
  "secondary_type": {"label":"电池类型", "enum":["LiFePO4","三元锂","钛酸锂"]},
  "quantity_value": {"label":"额定容量", "unit":"Ah"},
  "condition_text": {"label":"工作温度", "unit":"℃"}
}
```

### 5.3 Fallback

LLM 推不出 domain_schema → 退化为**空 schema**（4 槽位无 label/enum，纯通用骨架），不阻塞入库。后续检索退化为纯通用字段过滤。

### 5.4 人工修正

domain_schema 存 `gb_standard.domain_schema`，用户可在确认页修正。

## 6. LLM 批量抽取（核心优化：1 次调用产 4 类结果）

### 6.1 为什么合并成 1 次 batch

旧设计 5 个独立抽取器 × N 条款 = 5N 次 LLM 调用，成本爆炸。新设计：1 次调用打包 N 个条款，LLM 返回结构化结果，内部拆出 4 类输出。

### 6.2 单次 batch 的输入输出

**输入**（1 次调用）：
```json
{
  "domain_schema": { /* §5.2 推导结果 */ },
  "clauses": [
    {"clause_path":"9.2", "text":"过压充电保护：电池组..."},
    {"clause_path":"9.2.1", "text":"除...外，n 个单体..."}
  ]
}
```

**输出**（1 次调用同时产出）：
```json
{
  "results": [
    {
      "clause_path": "9.2",
      "slots": {"primary_type":"overcharge","secondary_type":"pack","quantity_value":null,"condition_text":null},
      "polarity": "positive",
      "exception_of": null,
      "parameters": [{"param_name":"overcharge_threshold","formula_display":"U = n × 6.0 V","unit":"V"}],
      "references": [{"target_type":"intra","target_clause_path":"4.5.1","ref_type":"prerequisite"}]
    }
  ]
}
```

### 6.3 正则预筛 + LLM 补充

为降低 LLM 负担，**先用正则抽确定的东西**：
- 条款号、标准号引用（`GB/T 31467.3`、`§4.5.1`）→ 正则
- 数值（`6.0V`、`25±5℃`）→ 正则
- LLM 只补**复杂语义**（槽位归类、极性判断、参数语义、引用关系语义）

正则结果作为 hint 传给 LLM，减少 LLM 推理量。

### 6.4 batch 大小

`batch_size = 10`（配置项 `jeecg.airag.gb-standard.clause-metadata-extractor.batch-size`）。一份 300 条款的国标 = ceil(300/10) = 30 次 LLM 调用（对比旧设计 5×300=1500 次）。

## 7. 双写

### 7.1 结构化表

- gb_standard：domain_schema + normative_refs
- gb_clause：层级树 + 4 槽位 + 极性
- gb_parameter：参数/公式（结构化）
- gb_reference：引用关系
- gb_term_dict：术语（来自第3章正则提取）

### 7.2 向量库（airag_embedding）

向量 chunk 的 metadata 注入：
```
standard_no, clause_path, chapter, polarity, primary_type, secondary_type, status
```
这些键与 `EmbeddingHandler.buildMetadataFilter` 的过滤键一致，供 VectorChannel 做 metadata 精排。

## 8. 审计埋点（P2 强制）

每条款入库记录写 `gb_audit_log`：
- session_id：入库批次
- user_query：留空（入库非查询）
- retrieved_clauses：本次入库的条款列表
- success：是否成功

埋点从 P2 开始，为 L5 评测提供数据基础（见 `01-设计总纲 §3` L5 注释）。

## 9. 配置与 Kill Switch

```yaml
jeecg:
  airag:
    gb-standard:
      enabled: true                       # 总开关（默认 false，部署时显式开启）
      user-review-enabled: true           # 用户确认页
      structure-parser:
        enabled: true
        llm-fallback: true                # 正则失败时才调 LLM
      schema-deriver:
        enabled: true
        model-name: "qwen-flash"          # 轻量模型
      clause-metadata-extractor:
        enabled: true
        batch-size: 10
        model-name: "qwen-flash"
      param-extractor: {enabled: true}    # 合并进 batch，开关仅控制是否产 param
      reference-extractor: {enabled: true}# 合并进 batch
      polarity-annotator: {enabled: true} # 合并进 batch
```

Kill Switch：任一开关置 false，对应能力跳过，不阻塞主管线（退化为通用骨架字段）。
