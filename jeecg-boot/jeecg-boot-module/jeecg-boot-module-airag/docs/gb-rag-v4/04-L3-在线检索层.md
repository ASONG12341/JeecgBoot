# 04 · L3 在线检索层

> **日期**：2026-07-15
> **解决根因**：1（语义≠逻辑）、6（线性≠树状）、8（引用断裂）、9（极性）、10（术语）、11（数值）
> **核心设计**：规则路由（快）+ LLM 槽位抽取（慢，可异步）→ 3 通道 RRF 加权融合 → 引用上下文增强

---

## 1. 检索流程总览

```
用户 query + knowId
      │
      ├─① 规则路由意图（<1ms，正则/关键词）
      │     → CLAUSE_LOOKUP / PARAM_QUERY / SEMANTIC_SEARCH
      │     → 决定激活哪些通道
      │
      ├─② LLM 槽位抽取（~2s，可异步并行启动）
      │     → 查 gb_standard.domain_schema
      │     → 拼动态 JSON Schema（通用骨架 + 4 槽位标签）
      │     → LLM Structured Output
      │     → QueryIntent{ 通用字段 + 4 槽位值 }
      │     → 带 fallback：LLM 挂了跳过②，退化为纯向量召回
      │
      ▼
 ③ QueryPlanner（用①的意图 + ②的槽位决定通道）
    ├── VectorChannel   （始终）
    ├── StructureChannel（意图=CLAUSE 或槽位含 clauseId）
    └── ParamChannel    （意图=PARAM 或槽位含 quantity_value）
    │   3 通道并行（CompletableFuture）
    ▼
 ④ RRF 加权融合（weightedFuse，通道权重真正生效）
    │
    ▼
 ⑤ ContextAssembler
    → 命中条款若 cites_external 非空 → 拉取被引用条款作【上下文增强】（不参与打分）
    → 引用强制注入：每条款格式化 [标准号 版本] §条款号 (页码)
    → 组装带来源标注的结构化上下文
```

**①②并行**：路由意图是快的，先用它启动 StructureChannel/ParamChannel；LLM 槽位结果是慢的，回来后给 VectorChannel 做 metadata 精排。两者 CompletableFuture 并行，不串行等待。

## 2. 意图两层分离（关键设计）

### 2.1 为什么分两层

旧 `AdaptiveIntentExtractor` 把"路由判断"和"领域槽位"混进一个 String enum。问题：
- "4.1.2 条是什么" → 明显 CLAUSE_LOOKUP，**正则一眼判断**，没必要花 2-3s 调 LLM。
- "3S 电池包过充测试" → 需要 LLM 抽 testType=overcharge（领域槽位）。

混在一起会让简单查询也付 LLM 延迟。分离后：简单查询走规则秒回，复杂查询才调 LLM。

### 2.2 第一层：规则路由意图（RoutingIntent）

| 判断 | 规则 | 路由意图 |
|------|------|---------|
| 含条款号正则（`4.1.2`/`第4章`/`附录A`） | 正则 | `CLAUSE_LOOKUP` |
| 含参数词（领域无关词：数值/公式/计算/等于/大于/小于/单位） | 关键词 | `PARAM_QUERY` |
| 其他 | 默认 | `SEMANTIC_SEARCH` |

> ⚠️ **关键词必须领域无关**。旧 `AdaptiveIntentExtractor` 用钢铁力学词（强度/硬度/屈服），这是 bug。路由层只用"数值/公式/计算"这类跨领域词。

### 2.3 第二层：LLM 槽位抽取（QueryIntent）

```
用户 query + domain_schema
   → 拼动态 JSON Schema（通用骨架字段 + 4 槽位的 label/enum）
   → LLM Structured Output
   → QueryIntent
```

**通用骨架字段**（所有标准共享，固定 Java 字段）：
- `standardNo` / `clauseId` / `version` / `objectType` / `isBooleanQuery`

**4 槽位**（固定字段，值由 LLM 按 domain_schema 填）：
- `primaryType` / `secondaryType` / `quantityValue` / `conditionText`

### 2.4 Fallback（宁可不精确，不要 0 召回）

LLM 槽位抽取失败的 6 种情况（超时/HTTP 错误/JSON 解析失败/Schema 不匹配/ResponseFormat 不支持/返回 null）→ 跳过②，QueryIntent 全 null。

此时 VectorChannel 退化为**纯向量召回 + knowledgeId 基础过滤**（不 0 召回）。监控 `airag_gb_intent_fallback_total{reason=...}`。

### 2.5 缓存

LLM 槽位结果按 query 文本 + knowId 缓存（短时，5 分钟 TTL）。重复 query 不重复调 LLM。缓存依赖待 P3 引入（当前 Caffeine/Redis 都未接入，见 pom）。

## 3. 统一意图系统（废弃两套并存）

### 3.1 现状问题

现在有两套互不相通的意图系统：
- POJO `GbQueryIntent`（电池字段焊死）接聊天 `AIChatHandler`
- String 枚举接检索页 `GbRetrievalController`

### 3.2 统一方案

**统一成一套 `QueryIntent`**（领域无关版）：
- 聊天链路（AIChatHandler）和检索页（GbRetrievalController）都用它。
- `GbQueryIntent`（电池 POJO）废弃，电池字段移到 domain_schema 数据。
- `AdaptiveIntentExtractor`（正则+钢铁词）废弃，路由逻辑进 `RoutingIntentClassifier`（领域无关词）。

### 3.3 废弃 ThreadLocal（重要 bug 修复）

现有 `IntentContext`（ThreadLocal）跨方法传意图。但 `GbRetrievalOrchestrator` 用 `CompletableFuture` + 固定线程池，**ThreadLocal 不跨线程传递**——检索编排读不到聊天链路设的 intent。

**修正 → 废弃 ThreadLocal，改显式参数传递**。QueryIntent 作为方法参数一路传下去，不靠 ThreadLocal。

## 4. 三个检索通道

| 通道 | 数据源 | 触发条件 | 权重 |
|------|--------|---------|------|
| VectorChannel | airag_embedding（pgvector + metadata 精排） | 始终 | 标准（0.4） |
| StructureChannel | gb_clause 表 | 路由=CLAUSE 或槽位含 clauseId/chapter | 最高（0.4，精确命中） |
| ParamChannel | gb_parameter 表 | 路由=PARAM 或槽位含 quantity_value | 次高（0.2） |

> GraphChannel **不在此列**——引用关系降级为 ContextAssembler 的上下文增强（见 §5），不参与 RRF 排序竞争。

### 4.1 VectorChannel（改：调带 intent 的 searchEmbedding）

**现状 bug**：`VectorChannel` 调 `searchEmbedding` 的 4 参数版本（不带 intent），导致 metadata 精排不生效。

**修正**：改调 5 参数版本 `searchEmbedding(knowId, query, topK, similarity, QueryIntent)`，让 `buildMetadataFilter` 生效（按 4 槽位 + clause_path + polarity 过滤）。

### 4.2 StructureChannel — 条款层级展开

```
精确匹配：用户提到 "9.2" → WHERE clause_path='9.2'
父条款展开：命中 9.2.1 → 自动包含 9.2（概述）提供上下文
子条款展开：命中 9.2 → 可选包含 9.2.1, 9.2.2 等子条款
引用展开：命中条款有 prerequisite 引用 → 自动包含被引用条款
```

### 4.3 ParamChannel — 结构化参数查询

查 `gb_parameter` 表：按 `param_name` 模糊 + `quantity_value` 范围。返回带公式展示串的结果。

## 5. ContextAssembler — 引用上下文增强 + 强制注入

### 5.1 引用关系作为上下文增强（不参与打分）

引用关系是**确定性上下文扩展**（条款 A 引用标准 B），不是**相关性竞争**。让它参与 RRF 打分会污染排序——被引用条款可能和 query 相关性低，但作为上下文必须给。

**设计**：
- 3 通道 RRF 融合后，对 top-K 命中条款检查 `cites_external` / `gb_reference`。
- 命中条款若有引用 → 拉取被引用条款作为**额外上下文**（标记 `[引用上下文]`，不参与打分）。
- 这取代了旧的 GraphChannel 概念。

### 5.2 引用强制注入（根因 13）

召回条款天然带 `clause_path`/`standard_no`/`version`/`page_no`。ContextAssembler 组装上下文时强制格式化：

```
[GB 31241-2022] §9.2 (p.15)
过压充电保护：电池组应...

[GB/T 31467.3-2015] §6.2 [引用上下文]
（被 9.2 引用，作为前置条件）
```

System Prompt 约束 LLM："回答必须引用上述标注的条款号"。

## 6. RRF 加权融合（weightedFuse，权重真正生效）

**现状 bug**：`RRFFusionStrategy.weightedFuse` 算了权重但编排器只调无权重的 `fuse()`——通道权重是摆设。

**修正**：编排器改调 `weightedFuse()`，通道权重（Vector 0.4 / Structure 0.4 / Param 0.2）真正生效。

RRF 公式（k=60）：
```
score(doc) = Σ_channel [ weight_channel × 1/(k + rank_channel(doc)) ]
```

去重：按 `clause_path` + `standard_id` 去重（同一条款多通道命中合并分数）。

## 7. 多标准混合检索的边界处理

一个知识库挂多份不同领域的国标：
- **意图槽位按命中的 standard 分别抽**，不强行合并异构 domain_schema。
- 具体做法：先 VectorChannel 粗召回确定涉及哪些 standard，再按 standard 分别抽槽位精排。
- 或：用户在检索时显式选标准（前端有标准选择器时），只抽该标准的 schema。

## 8. 版本/时效路由

- **默认只召回现行版**：`status=current`（根因 7）。
- 用户**显式提及旧版**（如"2014 版怎么规定"）→ 放开 status 过滤，按 version 路由。
- UUIDv7 时间有序，召回最新版本天然高效（无需额外排序）。

## 9. 与现有代码集成（AIChatHandler）

```java
public class AIChatHandler {
    // 聊天流也走 L3 检索（不只检索页）
    // extractAndCacheIntent → RoutingIntentClassifier + LLM 槽位抽取
    // → GbRetrievalOrchestrator.retrieve(query, knowIds, queryIntent)
    // → ContextAssembler 组装上下文 → LLM 生成
}
```

聊天流和检索页共用 `GbRetrievalOrchestrator`，区别只在最后一步：
- 检索页：返回 `RetrievalResponse`（结果列表 + 证据面板展示）
- 聊天流：ContextAssembler 上下文喂给 LLM 生成自然语言回答
