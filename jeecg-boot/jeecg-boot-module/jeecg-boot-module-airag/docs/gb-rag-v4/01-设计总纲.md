# 01 · 设计总纲

> **日期**：2026-07-15
> **状态**：v4 唯一设计源
> **替代**：`legacy/` 下所有历史设计稿

---

## 1. 问题本质

当前 airag 模块把国标当"普通文档"处理（扁平文本 → 向量 → 相似度匹配）。但国标是**法规级结构化文档**——有层级体系（章→条→款）、版本效力、跨标准引用、术语规范、极性条款、公式参数。14 类根因问题（详见 `legacy/GB-RAG-14根因复盘` §1）全部由此衍生。

## 2. 设计哲学：三个支柱

### 支柱一 · 领域无关（核心创新）

> **新增一份任何领域的国标（电池、储能、消防、建筑、食品），不修改任何 Java 代码、不新增任何字段枚举、不改任何 DDL。**

落地方式——**固定语义槽位**（详见 `02-L1`）。所有技术规范文档都有"做什么 / 对谁 / 多少 / 什么条件"四个共性维度，抽象成 4 个固定列：

| 槽位列 | 语义角色 | 电池示例 | 储能示例 | 消防示例 |
|--------|---------|---------|---------|---------|
| `primary_type` | 做什么 | overcharge | BMS功能 | 耐火试验 |
| `secondary_type` | 对谁 | cell | LiFePO4 | 防火门 |
| `quantity_value` | 多少 | 3 | 100 | 1.5 |
| `condition_text` | 什么条件 | 25±5℃ | -20℃ | 常温 |

领域差异全部下沉到 **`gb_standard.domain_schema` JSONB（纯数据、描述性）**：定义每个槽位在本标准里的标签和取值范围，但**不改变列名**。

```json
// domain_schema 只描述槽位语义，不定义字段名
{
  "primary_type":   {"label":"测试类型", "enum":["overcharge","short_circuit","crush"]},
  "secondary_type": {"label":"对象类型", "enum":["cell","pack","system"]},
  "quantity_value": {"label":"电池串数", "unit":"S"},
  "condition_text": {"label":"环境温度", "unit":"℃"}
}
```

**对比旧方案**：旧 `GbQueryIntent` POJO 把 `testType/nCells` 焊死在 Java 字段 + `@Description` 里列电池测试项 enum；旧 `AdaptiveIntentExtractor` 用钢铁力学词表。两者换领域都要改代码。新方案换领域只加一行 domain_schema 数据。

### 支柱二 · 文档驱动

所有领域知识来自文档本身：
- domain_schema 由 LLM 从标准前言/目录/前3章**推导**，而非人工预置。
- 条款的 4 槽位值由 LLM 在入库时抽取，符合所属标准的 domain_schema。
- 公式存 `gb_parameter` 表（值 + 展示串 + 变量），运行时由 Tool 计算，**不 eval LLM 字符串**。

### 支柱三 · 确定性优先

规则能做的事不交给 LLM；LLM 能做的事不交给概率检索：
- **结构解析**：正则+规则为主（国标条款号有规范格式），LLM 仅 fallback。
- **意图路由**：规则判断（"4.1.2条"→CLAUSE_LOOKUP，<1ms），LLM 只做领域槽位抽取。
- **算术**：Tool 用安全解析器算（不 eval，不信任 LLM 字符串），LLM 只解释结果。
- **引用**：召回条款天然带标准号/条款号，ContextAssembler 强制注入，System Prompt 约束必须引用。

## 3. 五层架构

```
┌─────────────────────────────────────────────────────────────────┐
│  L0  GitNexus 门禁层（强制，跨所有层）                            │
│      改任何符号前 impact；commit 前 detect_changes                │
│      HIGH/CRITICAL 风险须停下报告，不允许直接改                    │
├─────────────────────────────────────────────────────────────────┤
│  L5  评测与可观测层                                              │
│      审计追溯表（每条回答→来源条款→标准版本→页码）                 │
│      RAGAS 评测集 + LLM-as-Judge + 监控指标                      │
│      解决：根因 13（可解释性）、14（评测）                         │
│      ⚠ 审计埋点从 P2 开始（非 P4），否则无法量化改进              │
├─────────────────────────────────────────────────────────────────┤
│  L4  Tool Calling 层                                             │
│      GbCalculationTool（查 gb_parameter + 安全四则运算）          │
│      引用强制注入（ContextAssembler，非 Tool）                    │
│      System Prompt 约束（必须引用条款号、禁止自算数值）            │
│      解决：根因 2（算术幻觉）、13（证据链）                        │
├─────────────────────────────────────────────────────────────────┤
│  L3  在线检索层（Multi-Channel）                                  │
│      ① 规则路由意图（CLAUSE/PARAM/SEMANTIC，<1ms）               │
│      ② LLM 槽位抽取（4 槽位，可异步/可缓存/带 fallback）          │
│      → QueryPlanner → 3 通道并行 → RRF 加权融合                 │
│      → ContextAssembler（引用关系作为上下文增强，不参与打分）      │
│      解决：根因 1、6、8、9、10、11                                │
├─────────────────────────────────────────────────────────────────┤
│  L2  离线入库管线层                                              │
│      MinerU → 结构树解析（正则为主）→ 【用户确认页】             │
│      → LLM 批量抽取（schema 推导 + 4 槽位 + 极性 + 参数 + 引用）  │
│      → 双写（结构化表 + 向量库 metadata）                         │
│      解决：根因 3、4、5、9（离线侧）                              │
├─────────────────────────────────────────────────────────────────┤
│  L1  数据模型层（Ontology）                                       │
│      gb_standard(含 domain_schema) / gb_clause(含 4 槽位)        │
│      gb_parameter / gb_reference / gb_term_dict / gb_audit_log   │
│      + 现有 airag_embedding（metadata 增强）                      │
│      PG18：Skip Scan 多列索引 + UUIDv7 主键 + 虚拟生成列          │
└─────────────────────────────────────────────────────────────────┘
```

## 4. 与根因文档（legacy）的关键差异

本集继承根因文档的**问题分析**（14 根因成立），但**落地技术方案**有 8 处关键修订：

| # | 议题 | 根因文档（legacy） | 本集（v4） | 修订理由 |
|---|------|------------------|-----------|---------|
| 1 | 领域定位 | 电池安全专属（testType/nCells 焊死 POJO） | **领域无关**，固定 4 槽位 | 换储能/消防要改代码，不可持续 |
| 2 | 意图字段 | 固定 Java 字段 + enum | **通用骨架 + domain_schema 数据驱动** | 领域属性不能编译进 Java |
| 3 | 索引策略 | Skip Scan（但字段动态，矛盾） | **Skip Scan（固定槽位）+ GIN 兜底** | 动态键名无法 B-Tree 索引 |
| 4 | 公式 | `overcharge_threshold = n*6.0` 焊进 DDL 虚拟列 | **存 gb_parameter 表，Tool 运行时算** | 公式是领域知识，不能进 schema |
| 5 | LLM 抽取 | 5 个独立抽取器，每条款调 5 次 | **两阶段批量**：正则结构 + 1 次 batch LLM | 5N 次调用成本爆炸 |
| 6 | 意图系统 | 单一 LLM Structured Output | **路由意图(规则) + 槽位抽取(LLM) 分离** | 简单查询不该付 LLM 延迟 |
| 7 | 检索通道 | Graph 通道参与 RRF | **3 通道 RRF**，Graph 降级为上下文增强 | 引用是确定性扩展，不该参与排序竞争 |
| 8 | 评测 | P4 最后做 | **审计埋点前置到 P2**，P4 做看板 | 无法量化则无法改进 |

## 5. 核心原则（贯穿所有层）

1. **领域无关**：任何领域知识都在数据里，不在代码里。
2. **入库重提取**：结构化信息在 L2 入库阶段完成，检索时直接用，不现算。
3. **确定性优先**：规则 > LLM > 概率检索，能用确定性的不交给概率。
4. **多通道检索**：L3 不依赖单一向量，三通道并行 + RRF 加权融合。
5. **推理检索分离**：L4 Tool 负责确定性计算，LLM 只做语义理解。
6. **用户确认**：MinerU 解析质量不可控，结构确认后才跑 LLM 抽取（省 LLM 调用）。
7. **全程可审计**：L5 从 P2 起记录每条回答的完整证据链。
8. **可回滚**：每层每 Phase 有 Kill Switch，回滚独立。

## 6. 不做的事

- ❌ 用更大的上下文窗口覆盖多章——成本/失焦双重恶化
- ❌ 只用更好的向量模型替代——不能解决极性反转与逻辑互斥
- ❌ 任何 YAML 字典 + 正则做**领域槽位**抽取（路由意图仍可用正则）
- ❌ 自训领域模型——强规则文档应靠确定性工程
- ❌ 硬编码任何领域知识——全部数据驱动
- ❌ 公式 eval LLM 字符串——安全风险
- ❌ 破坏 airag 通用能力——国标增强层只在知识库为国标类型时激活
- ❌ 把领域公式焊进 DDL 虚拟生成列——公式归 L1 表数据，不归 schema
