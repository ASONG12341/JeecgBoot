# 07 · 分阶段实施路线

> **日期**：2026-07-15
> **目的**：把 v4 设计拆成可独立交付的 Phase，每个 Phase 有 Kill Switch、回滚方案、GitNexus 门禁。
> **核心原则**：审计埋点前置到 P2（非 P4），否则无法量化改进效果。

---

## 1. Phase 总览

| Phase | 内容 | 周期（估） | 依赖 | 风险 |
|-------|------|-----------|------|------|
| **P1** | L1 表结构 + PG18 Flyway 迁移 + domain_schema 设计 | 1 周 | PG18 已上线 ✅ | 低（新增表，不动存量） |
| **P2** | L2 入库管线（结构解析 + 确认页 + Schema 推导 + 批量抽取）+ 审计埋点 | 3-4 周 | P1 | 中（涉及 LLM 调用 + DDL） |
| **P3** | L3 检索层重构（统一 QueryIntent + 三通道 + weightedFuse + 上下文增强） | 2-3 周 | P1, P2 | 中-High（改检索链路） |
| **P4** | L4 Tool Calling + L5 评测看板 | 2 周 | P2, P3 | 低（旁路 + 评测） |

**总计**：8-10 周。每个 Phase 可独立交付、独立回滚。

---

## 2. P1 — L1 数据模型与 PG18 迁移

### 2.1 范围

1. 确认项目 Flyway 目录结构与命名规范（参考 jeecg-boot CLAUDE.md）
2. 写 Flyway 迁移 `V20260715__gb_rag_v4_schema.sql`：
   - CREATE EXTENSION btree_gist / pg_trgm
   - 6 张表（gb_standard / gb_clause / gb_parameter / gb_reference / gb_term_dict / gb_audit_log），见 `02-L1 §3`
   - 全部索引（Skip Scan 多列 + GIN + 虚拟生成列），见 `02-L1 §4`
   - airag_knowledge_doc 新增 `parse_status` 列
3. 实体类 + Mapper（MyBatis-Plus）对应 6 张表
4. domain_schema 的 JSON 结构定义（Java POJO + 校验）

### 2.2 Kill Switch

`jeecg.airag.gb-standard.enabled=false`（默认关）。表存在但不被任何代码引用。

### 2.3 回滚

`DROP TABLE gb_*` + `DROP COLUMN parse_status`。结构化表独立于 airag_embedding，删除不影响存量向量数据。

### 2.4 GitNexus 门禁

P1 是新建表 + 新建实体，blast radius = 0（不动既有符号）。但 Flyway 脚本要核对项目既有迁移顺序，避免版本号冲突。

## 3. P2 — L2 入库管线 + 审计埋点

### 3.1 范围

1. `GbDocumentStructureParser`（正则为主，LLM fallback）— 现有代码评估 + 完善
2. 用户确认页 `GbStandardPreview.vue` 完善（PDF.js 渲染）
3. `GbStandardController.confirm` 补全管线调用（现状仅翻 status）
4. `GbSchemaDeriver`（每标准 1 次 LLM 推 domain_schema）
5. `GbBatchExtractor`（1 次 batch 产 4 槽位 + 极性 + 参数 + 引用）
6. 双写：结构化表 + airag_embedding metadata
7. **审计埋点**：`gb_audit_log` mapper + 写入逻辑（每条款入库记录）

### 3.2 Kill Switch

```yaml
jeecg.airag.gb-standard:
  enabled: true
  structure-parser.llm-fallback: true   # 正则失败才调 LLM
  schema-deriver.enabled: true
  clause-metadata-extractor.enabled: true
```

任一开关 false → 对应能力跳过，退化为通用骨架字段，不阻塞入库。

### 3.3 回滚

Kill Switch（跳过 LLM 抽取），<1 分钟。结构化表数据可保留。

### 3.4 GitNexus 门禁

- `EmbeddingHandler.embeddingDocument`（写入路径，HIGH 风险：每条入库都走它）→ 必须先 impact
- 改前确认：metadata 注入新键（4 槽位）不影响存量读路径

---

## 4. P3 — L3 检索层重构

### 4.1 范围

1. 新建 `QueryIntent`（领域无关，通用骨架 + 4 槽位）
2. 新建 `RoutingIntentClassifier`（规则路由，领域无关词）
3. `DefaultGbIntentExtractor` → 重构为 `DefaultQueryIntentExtractor`（动态 schema 构造）
4. **废弃** `GbQueryIntent` / `IGbIntentExtractor` / `IntentContext`（ThreadLocal bug）
5. **废弃** `AdaptiveIntentExtractor`（钢铁词）
6. `VectorChannel` 改调 5 参数 searchEmbedding（metadata 精排生效）
7. `GbRetrievalOrchestrator` 改调 `weightedFuse` + 补 `@PreDestroy`
8. 新建 `ParamChannel`
9. 新建 `ContextAssembler`（引用上下文增强 + 强制注入）
10. `AIChatHandler` 重构意图接入（废弃 ThreadLocal，改显式传参）
11. 切换聊天流和检索页到新意图系统；切换后删旧代码

### 4.2 Kill Switch

```yaml
jeecg.airag.gb-standard:
  llm-intent-enabled: true        # LLM 槽位抽取开关
  retrieval:
    vector-weight: 0.4
    structure-weight: 0.4
    param-weight: 0.2
```

`llm-intent-enabled=false` → 跳过 LLM 槽位，退化为纯向量召回（不 0 召回）。

### 4.3 回滚

Kill Switch（退回纯向量检索），<1 分钟。

### 4.4 GitNexus 门禁（重点）

- `EmbeddingHandler.searchEmbedding` / `getQueryRouter`（HIGH：全检索链路）
- `AIChatHandler.completions` / `chat`（HIGH：全量 LLM 调用）
- `GbRetrievalOrchestrator.retrieve`（MEDIUM-HIGH）

HIGH/CRITICAL → 拆小 PR：先切 VectorChannel（只读路径），再切意图系统，最后切聊天流。

## 5. P4 — L4 Tool Calling + L5 评测

### 5.1 范围

1. `GbCalculationTool`（安全四则运算，查 gb_parameter）
2. 注册进 AIChatHandler（仅国标知识库时）
3. System Prompt 增强（必须引用条款号、禁止自算数值）
4. `GbCitationTool`（可选，默认关）
5. **L5 评测**：RAGAS 评测集 + LLM-as-Judge（依赖 P2 起的 audit log 数据）
6. 监控看板：召回率、引用准确率、fallback 命中率、计算准确率

### 5.2 Kill Switch

```yaml
jeecg.airag.gb-standard:
  tool:
    calc-enabled: true
    citation-tool-enabled: false   # 可选，默认关
```

### 5.3 回滚

不注册 Tool（LLM 不感知），<1 分钟。审计表数据保留。

### 5.4 GitNexus 门禁

- `AIChatHandler.completions`（HIGH：Tool 注册改 LLM 调用）
- Tool 是新类，blast radius = 0，但接入点 HIGH

## 6. 回滚矩阵（汇总）

| Phase | 主变更 | Kill Switch | 回滚耗时 | 数据影响 |
|-------|--------|------------|---------|---------|
| P1 | 新建表 + Flyway | `enabled=false` | <1 分钟 | 无（新表空） |
| P2 | L2 管线 + LLM 抽取 | 各抽取器开关 | <1 分钟 | 结构化表数据可保留 |
| P3 | L3 检索重构 | `llm-intent-enabled=false` | <1 分钟 | 无 |
| P4 | Tool Calling + 评测 | `tool.calc-enabled=false` | <1 分钟 | 审计表保留 |

**所有 Phase 回滚都 <1 分钟，且不丢数据**——这是设计时强制的约束。

## 7. 审计埋点前置说明（重要）

| 阶段 | 审计动作 |
|------|---------|
| **P2 起** | 每条款入库写 `gb_audit_log`（入库记录） |
| **P3 起** | 每次检索写 `gb_audit_log`（query + intent + channels + clauses + latency） |
| **P4 起** | 每次 Tool 调用写 `tool_calls` 字段；RAGAS 评测跑批读 audit log |

**为什么前置**：根因 14（评测缺失）是横切度量。若 P4 才埋点，P2/P3 改进效果无法量化（没有 before 数据）。所以埋点从 P2 起，P4 才做评测看板。

## 8. 验收标准（每 Phase）

| Phase | 验收点 |
|-------|--------|
| P1 | Flyway 迁移成功；6 表 + 索引建好；实体/Mapper 编译通过 |
| P2 | 上传一份测试 PDF → 确认页正确展示结构 → 确认后 gb_clause 有数据（含 4 槽位）；audit log 有入库记录 |
| P3 | 检索页查询返回正确结果；聊天流引用条款号；LLM 槽位 fallback 正常；weightedFuse 权重生效 |
| P4 | 数值问题走 Tool 返回精确值（非 LLM 幻觉）；RAGAS 指标有基线数据 |

每 Phase 验收前跑 GitNexus `detect_changes({scope: "compare", base_ref: "main"})` 确认变更范围。
