# 06 · 现有代码处置与迁移方案

> **日期**：2026-07-15
> **目的**：盘点现有 GB-RAG 代码，给出保留/重构/废弃的明确处置，指导后续 plan 执行。
> **原则**：能复用的复用（省工作量），领域硬编码的废弃，有 bug 的修正。

---

## 1. 现状：三套打架的方案

代码里实际存在三套互不相通的"意图 + 检索"方案，是"越改越乱"的技术根源：

| | 意图抽取方式 | 领域定位 | 出处 | 状态 |
|---|---|---|---|---|
| ① 根因文档方案 | LLM Structured Output + 固定电池字段(testType/nCells) | 电池安全专属 | `legacy/GB-RAG-14根因复盘.md` | 文档，未完全落地 |
| ② 7-14 设计文档方案 | 动态 JSON Schema 从文档推导 | 领域无关 | `legacy/2026-07-14-gb-standard-rag-engine-design.md` | 文档，v4 继承其思路 |
| ③ 实际写的代码 | 正则 + 钢铁力学词关键词 | 啥也不是 | `AdaptiveIntentExtractor.java` | **代码，违反①②** |

**v4 的决策**：以②为骨架（领域无关），修正②与代码的脱节，并补全①里和领域无关的技术点。

## 4. 迁移顺序（与 07 实施路线对齐）

1. **P1**：先建新表（Flyway V20260715），不动旧代码。旧代码继续运行（kill switch 默认关）。
2. **P2**：L2 入库管线 + domain_schema 抽取，新数据进新表。
3. **P3**：L3 检索层重构（统一 QueryIntent），切换聊天流和检索页到新意图系统。旧 `GbQueryIntent`/`AdaptiveIntentExtractor` 在切换后删除。
4. **P4**：L4 Tool Calling + L5 评测。

**关键**：旧代码切换前保留可用（可回滚）；切换在新代码验证通过后一次性完成，避免半新半旧并存。

## 5. GitNexus 门禁（强制，对应 L0）

处置表里每个"重构/修正"的 Java 类，实施前必须先跑：

```
mcp__gitnexus__impact({target: "类名.方法名", direction: "upstream", summaryOnly: true})
```

重点高影响符号（预期 HIGH/CRITICAL）：
- `EmbeddingHandler.searchEmbedding` / `getQueryRouter`（全知识库检索链路）
- `AIChatHandler.completions` / `chat`（全量 LLM 调用）
- `GbRetrievalOrchestrator.retrieve`（检索编排）

HIGH/CRITICAL 风险时停下报告，拆小 PR。
